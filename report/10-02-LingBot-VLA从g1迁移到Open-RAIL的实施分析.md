# LingBot-VLA 从 g1 迁移到 Open-RAIL：需要改什么、为什么改、怎样验证

分析日期：2026-10-02。本文直接检查本地 `g1-open-rail`、`g1`、`lingbot-vla` 的部署源码、配置和本机 SDK 接口。没有启动模型、连接机器人、安装依赖或修改控制代码；下面的新文件和新参数都是实施建议，尚未创建或实现。

文中的 LingBot-VLA 指你所说的“linbovla”。目标是：**保留目前训练好的软包任务模型，让 Open-RAIL 接管观察现场、请求模型、安排动作、控制 G1 和记录运行的工作。** 不需要为此重新训练模型，也不需要把整个 `g1` 仓库复制过来。

**本次不迁移 RTC。LingBot 使用普通推理，执行调度直接采用 Open-RAIL 已有能力。超时、发送节奏、暂停和记录都已存在，不列为需要重新开发的功能。** 下文区分“模型接入必须改”“任务参数需要配置”和“有额外需求时才扩展”，不再把框架改进全部列为迁移前提。

## 1 先给结论：能迁移 但不是添加一个模型名称就完成

Open-RAIL 确实支持接入自己的模型。它要求新增一个 `ModelVLA` 类：输入是一份观测，输出是未来一串动作。模型怎样加载、原来用什么通信方式，都可以由这个类处理。

**建议第一阶段继续运行目前的 LingBot 模型服务，在 Open-RAIL 内新增一个“翻译并转发请求”的模块。** 这样继续使用原来的权重加载、图像预处理和动作数值恢复，先验证更换执行框架带来的变化。以后需要减少中间通信，再考虑把模型直接加载进 Open-RAIL 服务进程。

需要分清三个完成程度：

| 完成程度 | 可以证明什么 | 还不能证明什么 |
| --- | --- | --- |
| 模型接通 | Open-RAIL 能发送图像和状态，收到 `[50,16]` 动作数组 | 图像颜色正确、夹爪行为一致、机器人能正常执行 |
| 执行含义对齐 | 模型输入与原部署一致，最终手臂与夹爪命令遵守同样约定 | 边执行边计算后一定更流畅，或者抓取成功率一定更高 |
| 完成实机迁移 | 相同任务下能持续执行，退出与异常处理正常，记录可还原实际命令 | 所有参数都适合其他模型、其他任务或其他 G1 |

其中 `[50,16]` 的意思是：模型一次给出 50 个未来时间点，每个时间点有 14 个手臂关节角度和左右两个夹爪目标。它是一份未来计划，不是 50 次模型推理。

**最小的模型接入涉及 4 个文件；当前机器还需适配夹爪等任务差异，并配置执行参数、任务文字和记录格式。Open-RAIL 的调度、暂停和记录模块原则上复用。** 具体文件清单见第 4 章。

依据：[仓库的自定义模型指南](../docs/guides/add-new-model.md)、[模型注册配置](../conf/models_conf.py)、[模型服务启动入口](../run_server.py)。

## 2 迁移后 谁负责哪一段工作

### 2.1 目前 g1 的链路

```text
G1 相机与关节反馈
  → g1_native_vla_deploy.py 整理输入
  → WebSocket，通常是 8006 端口
  → LingBot 服务加载模型、计算动作、恢复数值
  → 返回 action，通常是 50×16
  → g1 的串行或实时程序选取要执行的目标
  → 厂家 SDK → G1 内部运控 → 机器人运动
  → 新图像、新状态进入下一轮
```

其中模型本体不在 `g1` 里，而在相邻的 `lingbot-vla` 仓库。`g1` 主要提供连接机器人和安排执行的程序。

### 2.2 推荐迁移后的链路

```text
G1 相机与关节反馈
  → Open-RAIL 的 RobotBody：读取并配对观测
  → Open-RAIL 的 VLAClient：整理图像与任务文字
  → ZMQ，通常是 5566 端口
  → Open-RAIL 的 VLAServer：解码图像
  → 新增 LingBot ModelVLA：转换字段并转发
  → WebSocket，通常是 8006 端口
  → 原来的 LingBot 服务：计算动作
  → 新增 ModelVLA：将 action 包装为 pred_action
  → Open-RAIL 客户端：安排时间、处理动作衔接
  → RobotProxy 转交给机器人工作进程
  → RobotBody 检查并生成实际 SDK 参数
  → SDK → G1 内部运控 → 新图像与反馈
```

ZMQ 和 WebSocket 是两种程序间传消息的方法。它们不能只靠改端口互相通信，新增模块负责把两种消息格式接起来。

迁移后，**实际动作的时间安排由 Open-RAIL 负责**。旧的 `g1_native_vla_deploy.py` 和 `g1_realtime_chunking.py` 不应再作为另一个控制程序同时运行，否则两个程序可能交替发送不同目标。

但是当前机器的网络准备、COPILOT 模式切换和 SDK 环境仍有用，可以先继续使用 `g1` 的相关工具。替换执行客户端，不等于机器人端也要重新部署一套控制器。

### 2.3 为什么先保留 LingBot 独立服务

| 方案 | 怎么实现 | 好处与代价 |
| --- | --- | --- |
| **方案 A：转发到现有模型服务，建议先做** | 新适配类持有 WebSocket 客户端，调用现有 LingBot 服务 | 不必重装整套模型环境；容易和旧部署比较。但多一层传输、一次数组打包，必须测量新增耗时。 |
| 方案 B：模型直接加载到 Open-RAIL 服务 | 新适配类导入 `LingbotVLAServer`，直接调用其 `reset()` 和 `infer()` | 去掉一段 WebSocket 通信；但要在模型环境中安装 Open-RAIL 服务依赖，处理导入路径和依赖兼容。 |
| 方案 C：让 Open-RAIL 客户端直接改用 LingBot WebSocket | 重写客户端请求层，绕过 Open-RAIL 模型服务 | 改动会涉及请求编号、超时、心跳和响应格式。对本次迁移没有必要。 |

方案 B 也应复用现有 `LingbotVLAServer`，而不是另写一遍模型加载和预处理。它已处理训练配置、LoRA 权重结构、归一化统计、图像尺寸和输出恢复，这些都是“同一个模型是否仍按原来方式工作”的一部分。

依据：[原部署输入与执行](/home/bjtc/Sophix/g1/运控test/g1_native_vla_deploy.py:177)、[LingBot 服务](/home/bjtc/Sophix/lingbot-vla/deploy/lingbot_vla_policy.py:138)、[Open-RAIL 服务分发](../server/core/vla_server.py:140)。

## 3 先把输入与输出的含义对齐

### 3.1 输入字段怎样对应

Open-RAIL 服务交给适配器的是 `sequence`，通常只有一份观测。第一阶段关闭历史图像输入，只接受一份，避免悄悄丢弃多帧输入。

| Open-RAIL 解码后的内容 | 转给 LingBot 的字段 | 需要检查什么 |
| --- | --- | --- |
| `sequence[0]['obs']['state']` 的双臂和双夹爪部分 | `observation.state` | 严格按左臂 7、右臂 7、左夹爪、右夹爪排列，共 16 个数 |
| `obs['cam.head']` | `observation.images.cam_high_rgb` | 头部图像，红绿蓝顺序，H×W×3 数组 |
| `obs['cam.hand_left']` | `observation.images.cam_left_wrist_rgb` | 左腕图像，不能与右腕交换 |
| `obs['cam.hand_right']` | `observation.images.cam_right_wrist_rgb` | 右腕图像 |
| `obs['language'][0]` | `task` | 传字符串，不把整个列表或默认的泡茶指令交给软包模型 |

Open-RAIL 当前读取的状态还包括头和腰，通常共有 20 个数；LingBot 的这项任务只要其中前 16 个。**推荐保留机器人侧完整状态供界面和手动操作使用，在模型适配器中明确选择前 16 个。** 这个选择成立的前提是读取顺序仍为 `arm, gripper, head, waist`，启动时应核对，不能无条件截断任何数组。

模型输入中的夹爪反馈应继续使用厂家原始的 0～120 数值。Open-RAIL 的 `obs.state` 保留原值，适合在这里选取；界面所用的 `current_state` 则会换算夹爪数值，不能拿它直接替代模型输入。

依据：[G1 的状态读取顺序](../conf/robots_conf.py:27)、[RobotBody 观测读取](../client/robots/agibot_g1/body_robot.py:130)、[LingBot 软包任务字段定义](/home/bjtc/Sophix/lingbot-vla/configs/robot_configs/package_a2d.yaml)。

### 3.2 不能漏掉模型初始化时的 reset

原 `g1` 在连接后会执行：

```python
client.reset("package_a2d")
```

这里的 reset 是**告诉模型采用哪套机器人输入输出定义，并初始化数据变换**，不是让机器人回到起始姿态。LingBot 根据 `package_a2d.yaml` 建立 `FeatureTransform`；如果没做这一步，后面的图像处理和推理会用不到所需的转换对象。

新增适配器至少应在首次连接后执行它，重新建立连接后也应保证初始化正确。第一阶段让一个适配器独占一个模型会话，不同时服务不同机器人任务。

Open-RAIL 网页上的机器人复位与 LingBot 的 reset 不是同一操作。这里需要的是连接后的模型初始化，不是改写网页暂停或机器人复位流程。

依据：[原部署的 reset 调用](/home/bjtc/Sophix/g1/运控test/g1_native_vla_deploy.py:511)、[LingBot reset 实现](/home/bjtc/Sophix/lingbot-vla/deploy/lingbot_vla_policy.py:260)。

### 3.3 模型输出已经恢复成关节目标 不要再加一次当前位置

训练时手臂动作使用了相对状态的表示；但 LingBot 服务的 `FeatureTransform.unapply()` 已经将其恢复成绝对关节目标。

所以适配器拿到 `response['action']` 后，应当：

1. 检查形状为约定的 `[50,16]` 或 `[25,16]`。
2. 检查所有数值有效，不能包含 NaN、无穷大。
3. 保留 14 个手臂角度的含义，不再加当前角度，不再重复做归一化恢复。
4. 将数组以 `pred_action` 返回给 Open-RAIL；最终夹爪限幅和左夹爪保持策略在机器人执行侧统一实施。

适配器对外返回的基本格式如下：

```python
{
    "type": "vla_action",
    "pred_action": action,               # 50×16 或约定的 25×16
    "ref_timestamp": data["ref_timestamp"],
    "loc_timestamp": data["loc_timestamp"],
    "ext": {},
}
```

两个时间字段必须原样带回，不能替换成“推理结束时间”。客户端依靠它们判断新计划是多久之前的观测产生的；改成返回时刻，会让旧计划看起来过于新鲜。`ref_timestamp` 来自观测参考时间，`loc_timestamp` 是客户端记录的本地计时值，两者也不能混用单位。

请求编号不需要塞进动作数组。当前 `VLAServer` 会把请求的 `meta` 带回，其中含有 `request_id`；保留这条机制即可避免客户端接错上一轮迟到的结果。

依据：[LingBot 输出恢复](/home/bjtc/Sophix/lingbot-vla/deploy/lingbot_vla_policy.py:91)、[Open-RAIL 响应回调](../server/core/vla_server.py:217)、[客户端请求匹配](../client/core/vla_client.py:980)。

模型配置至少说明：连接方式、LingBot 地址与端口、机器人定义名称 `package_a2d`、预期动作长度 50 或 25、动作维度 16、连接和请求等待上限、LingBot 仓库路径，以及用于标识模型的 `model_path`。

**`model_path` 不能省略。** 当前 `VLAServer.__init__()` 直接读取 `model.cfg['model_path']` 来显示服务信息，因此新类要保存 `self.cfg`，配置也要提供该字段。

但方案 A 中，这个路径只是桥接服务记录的模型标识；真正加载哪个权重，由已经启动的 LingBot 服务决定。修改 Open-RAIL 的 `--model_path` **不会远程让 LingBot 换模型**。应通过启动脚本统一两端配置，或扩展服务元信息后核对两端是否一致，避免界面显示模型 A，实际运行模型 B。

适配器宜调用一个专门的轻量通信模块，例如新增 `server/models/lingbot_vla/native_client.py`。可以复用现有 LingBot 的消息打包与通信代码，但要补上第 6 章说明的超时和重连处理；不要只复制没有等待上限的实现。

另一个配置限制是：`web_client/server.py` 的 `_apply_flat_patch_new()` 只覆盖已有配置字段。对于确实需要新增的“关闭夹爪增强”等参数，要先在 Python 配置构造函数中定义，再在执行代码中读取。只往 YAML 写一个新名字不会自动实现新功能。

## 5 最容易出现“接通了 但机器人做得不对”的地方

### 5.1 左夹爪不能突然改为跟随模型

旧部署只采用模型的右夹爪目标。左夹爪在每轮开始读取一次位置，换算为 `raw/120` 后保持。

Open-RAIL 当前 `control_robot()` 会把模型给出的两个夹爪目标都交给 SDK，而且还用四次方公式增强开闭趋势。因此直接接上模型，会同时改变左右夹爪行为。

建议将执行侧明确分成两种模式：

- 普通任务：保留原 Open-RAIL 行为。
- LingBot 软包任务：左侧使用明确采样的保持目标；右侧使用模型目标，只限制到 0～1，不做四次方增强。

如果要严格保持旧程序“每轮开始重新测量左夹爪”的行为，需要把“新动作段开始”这一事件传到执行侧；现在 `control_robot(action)` 只收到一帧数组，没有动作段编号。若首版选择“开始一次任务时取保持值”，也要写入配置和实验记录，因为这不是完全相同的策略。不要把每个控制周期不断追随反馈误称为固定保持。

还应统一手动操作所用的夹爪换算。Open-RAIL 的界面状态采用 `(raw-35)/85`，旧任务采用 `raw/120`。例如 raw=35，前者是 0，后者约为 0.292。两种换算不能混入同一条自动执行链。

依据：[Open-RAIL 夹爪执行](../client/robots/agibot_g1/body_robot.py:58)、[旧部署保持左夹爪](/home/bjtc/Sophix/g1/运控test/g1_native_vla_deploy.py:289)、[SDK 夹爪输入处理](/home/bjtc/Sophix/g1/vendor_packages/a2d_sdk-1.5.0/.venv/lib/python3.10/site-packages/a2d_sdk/robot.py:710)。

### 5.2 夹爪目标在多个位置会被修改

只关闭 RobotBody 的增强公式仍不够：

| 所在位置 | 会怎样影响夹爪 | 迁移初期怎样处理 |
| --- | --- | --- |
| `intra_chunk_smoother.py` 的拟合分支 | 对相邻多个夹爪目标取平均，再把接近两端的数值改为 0 或 1 | 对照阶段先绕过；需要手臂拟合时，单独保留夹爪的原始开合变化 |
| `realtime_data_manager.py` 的 `gripper_offset` | 将夹爪目标在处理后的序列中向前或向后移动 | 先设为 0，避免无意改变抓取时机 |
| `body_robot.py` 的四次方公式 | 使中间开度更偏向全开或全闭 | 对软包任务关闭 |
| `body_robot.py` 的 `gripper_freq` | 每调用若干次才实际发送一次夹爪命令 | 按最终发送间隔选择；该字段不是“每秒几次” |
| `robot_proxy.py` 的最新目标合并 | 来不及执行的旧目标会被更新目标覆盖 | 验证短暂的闭合/松开是否仍完整执行 |

默认 `gripper_freq=40` 表示每 40 次调用才发送。若手臂目标每秒发 30 次，夹爪约每 1.33 秒才发一次，显然不同于旧部署每帧发送。用于 30 次/秒的对照配置时，应设为 1，并在假 SDK 中核对实际次数。以后增加手臂发送频率，也要重新计算这项设置。

### 5.3 图像应在模型入口比较 不能只看网页颜色

旧 `g1` 根据相机数据包的编码和颜色信息，生成 RGB 图像，再发给 LingBot。Open-RAIL 则经历：

```text
SDK 图像 → RobotBody 交换颜色通道 → 客户端图像处理
→ JPEG 编码 → 服务端解码并交换通道 → 模型适配器
```

这条链可能得到正确颜色，但要结合 SDK 实际返回格式验证，不能仅靠注释判断。特别是 `VLAServer` 中交换通道的注释写法不能作为最终颜色正确的证据。

推荐明确每个接口的颜色约定：RobotBody 给 OpenCV 编码的图像按它所需的顺序准备；模型适配器拿到的则固定是 RGB。对最近时间点的腕部图像，需要同时保留对应数据包或可核对的采样时间，不要拿另一次最新数据包解释旧图像。

此外，Open-RAIL 默认先调整图像尺寸，并使用质量 80 的 JPEG；LingBot 自己还会用 PIL 调整到训练配置要求的尺寸。两次调整加有损压缩，会让新链路的模型输入不同于旧部署。

迁移时先配置图像尺寸并验证颜色，现有 JPEG 传输可以继续使用。如果要精确比较两条路径的像素差，再关闭 Open-RAIL 额外缩放和服务端补边缩放，并考虑增加 PNG 等无损传输选项。PNG 开关需要接入 `_process_image_thread_func()`；这是精细对照的可选工具，不是接入 LingBot 的前置要求。

验证时在 **LingBot 的 `infer()` 开始处理前** 保存三路输入，比较颜色、尺寸、相机顺序和像素差；JPEG 条件下不要求逐像素相等。

依据：[旧部署颜色处理](/home/bjtc/Sophix/g1/运控test/g1_native_vla_deploy.py:152)、[Open-RAIL 图像编码](../client/core/vla_client.py:834)、[服务端解码](../server/core/vla_server.py:111)、[LingBot resize_image](/home/bjtc/Sophix/lingbot-vla/deploy/lingbot_vla_policy.py:288)。

### 5.4 动作数组 16 列 不需要为了界面补成 22 列

Open-RAIL 的 G1 动作表共有 22 个位置，但其中头、腰、底盘属于手动部分。`parse_action_layout()` 会把这些部分排除在模型动作之外；模型动作仍可以只有 16 列。

因此不要在模型输出后简单补六个零。补零可能使执行端认为模型确实发来了头或腰的目标，并调用对应接口。保持模型输出 16 列，保留手动部分配置即可。

完整状态可以是 20 个数，模型动作可以是 16 个数，界面动作表可以覆盖 22 个位置。三者用途不同，不要求长度相同。

依据：[动作表解析](../client/utils/util.py:176)、[根据实际长度拆分控制部位](../client/robots/agibot_g1/body_robot.py:65)。

### 5.5 换成 raw 不等于恢复原来的 30 次/秒执行

模型按每秒 30 个目标生成计划，相邻目标预计相隔约 33.33 毫秒。Open-RAIL 默认计划每 3.75 毫秒取一次处理后的目标，配合更密的曲线点使用。

如果只把处理方式改成 `raw`，即原样保留 50 个目标，却保留 3.75 毫秒的取点周期，当前索引逻辑会在每次调用时前进一步。这样约 1.67 秒的一份模型计划，可能在约 0.19 秒内被取完。这不是模型变快，而是播放速度错了。

对照阶段若使用原始点，应让控制周期与 30 个目标/秒相匹配，即约 33.33 毫秒，并将 `speed=1`。但仍要测试首个点和末个点：当前 `get_action_fitted()` 先增加索引再读取，初始索引为 0 时首次可能取到第 1 点；它也会在末点持续返回最后位置。这些细节使“raw + 30Hz”仍不自动等价于旧程序逐点执行。

后续想让手臂走更小的步，可以在 30 个模型目标之间计算中间位置，再提高取点频率。那是新增动作处理，应独立比较，不能作为“无变化迁移”混在第一步里。

依据：[原始点分支](../client/core/intra_chunk_smoother.py:417)、[按调用递增的索引](../client/core/realtime_data_manager.py:346)、[模型时间间隔设置](../client/core/vla_client.py:217)。

### 5.6 原来“每轮执行前 N 个”没有直接对应的配置

旧 `g1` 收到 50 个目标后，可以只执行前 30 个，历史某些运行只执行前 15 个，再重新看现场。Open-RAIL 的同步模式通常等处理后的动作段走到末尾，异步模式则在推理完成并等待一小段时间后继续请求。

所以以下几项不是一回事：模型输出长度 50；当前准备执行多少个目标；什么时候请求下一段；请求返回后跳过多少旧目标。

本次采用 Open-RAIL 原有调度，不必复制旧程序“每轮执行前 N 个”的规则。只有另外要求完全复现旧串行基线时，才需要新增明确的执行前缀规则，并测试选点与计时。可以在适配器返回时暂时截取前 N 个，但这样会把执行策略放入模型接入层，也失去其余未来动作，不宜作为长期方案。

Open-RAIL 中的 `rdm.mode=async` 表示旧动作执行时可以算新动作。本次可直接使用它，不必迁移旧 `g1` 的 `async-skip` 实现。

## 6 新增的 LingBot 连接需要处理什么

### 6.1 同一个 WebSocket 不要同时收发两份推理

Open-RAIL 默认 `max_infer_workers=3`。而 LingBot 的 `WebsocketClientPolicy` 使用一条连接，执行顺序是“发一份请求，然后接一份结果”，没有为并发调用分配响应。

如果三个线程同时使用它，可能抢收响应或触发通信库错误；reset 与推理也可能相互影响。首版应使用单个推理工作线程，并在适配器内部保护连接，使 reset、infer 和重连不能交叉进行。

单线程和锁解决的是同一连接被同时使用的问题。验证时还应模拟模型变慢、外层请求超时：若出现旧请求积压，就在新适配器或请求入口限制接收并拒绝过时工作；这项异常治理可以单独实施，不表示普通接入必须先重写整个服务队列。已经开始的 GPU 推理通常不能因为客户端超时就立即取消，要区分“不再采用结果”和“计算真正停止”。

### 6.2 Open-RAIL 已有超时 新增 WebSocket 连接也要有等待上限

Open-RAIL 的请求超时已经存在，继续复用。采用本文推荐的转发方案后，会多出一段它不能直接控制的等待：

```text
Open-RAIL 客户端等待桥接服务
桥接服务等待 LingBot WebSocket 答复
```

现有 LingBot 客户端的 `recv()` 没有显式等待上限，连接失败也会每 5 秒重试。原样复用会出现：Open-RAIL 已经宣布请求超时，但桥接线程还一直等着，后面的请求持续积压。

建议给连接、接收服务元信息、reset 和 infer 分别设置有限等待；WebSocket 等待超时后关闭这条连接，重建连接并初始化，再处理后续新请求。不要让下一次请求继续从旧连接读到上一份迟到结果。

外层等待上限要覆盖正常的图像处理、排队、模型计算和返回时间，并留合理余量。Open-RAIL 当前普通等待是 500 毫秒，首次为其四倍；不能根据旧报告中“块间约半秒”就直接定模型超时，因为那个时间包含取图、日志等其他工作。

若 GPU 推理没有结束，不应通过不停重连提交更多计算。首版新适配器至少要限制重试，失败后明确报错；通用服务端忙碌状态、错误协议和队列改造属于进一步完善。若选择直接加载模型的方案 B，就没有新增的 WebSocket 等待层，也不需要实现这层连接超时。

### 6.3 心跳正常不代表模型还能算

Open-RAIL 的心跳由它自己的 ZMQ 服务提供。即使后面的 LingBot 断开，桥接进程仍可能回应心跳。

排查时应区分“Open-RAIL 服务连通”和“LingBot 最近一次推理成功”。首版可通过新适配器日志显示后者；网页增加专门状态属于可选改进，不是必须重做心跳功能。

依据：[推理线程池](../server/core/vla_server.py:40)、[当前 LingBot WebSocket 客户端](/home/bjtc/Sophix/lingbot-vla/deploy/websocket_client_policy.py:14)、[Open-RAIL 超时配置](../conf/zmq_conf.py)、[客户端首次请求](../client/core/vla_client.py:635)。

## 7 启动环境与任务配置怎样迁移

### 7.1 三个进程 可以继续使用不同环境

| 进程 | 所需环境 | 是否直接访问机器人 |
| --- | --- | --- |
| LingBot 模型服务 | 现有 `lingbot-vla` 模型环境、GPU 依赖、权重和对应统计文件 | 否 |
| Open-RAIL 模型桥接服务 | Open-RAIL 服务依赖和轻量 WebSocket/数组打包依赖 | 否 |
| Open-RAIL Web 客户端及其机器人工作进程 | Open-RAIL 客户端依赖、可用的厂家 SDK 和机器人网络环境 | 是 |

Open-RAIL 把 SDK 放进独立进程，不代表它自动使用另一个虚拟环境。当前采用 Python 的 `spawn` 创建子进程，通常仍沿用启动 Web 客户端的解释器。因此这个解释器必须能够导入 SDK；本机 Cosine 的安装包与 Python 3.10 有关，不能只看到 Open-RAIL 写着支持 Python 3.10 以上，就任意换到别的版本。

`g1/g1_pc_gdk_env.sh` 会激活现有 GDK 环境并设置网络变量。初期可复用它；若要不改动原环境，则建立独立的 Python 3.10 客户端环境，安装同版本 SDK 与 Open-RAIL 依赖，再复用网络变量设置。不要只复制 `.venv` 目录，也不要在未核对版本前对原 GDK 环境整体升级。

本机 SDK 已有按参考时间取相机、手臂、夹爪、头、腰数据的接口，Open-RAIL 的 G1 读取方式有对应基础。不过这只是源码接口存在，仍要在新环境实际验证状态和图像能够到达。

仓库里的 `scripts/run_a2d_sdk.zsh` 假设另一个相对目录与服务启动方式，不能直接代替目前 `g1` 的机器准备脚本。

### 7.2 当前实际入口是 Web 客户端

本仓库现有入口是：

```bash
python run_web_client.py --conf lingbot_package.yaml
```

它从仓库 `conf` 目录读取这个 YAML。应从 Open-RAIL 根目录启动，并使用前述已经准备好的 Python 环境。

`conf/user_conf_example.py` 中的 `python run_client.py --user_conf ...` 是旧用法；当前工作区没有 `run_client.py`。不要照这个例子编写迁移启动脚本。

另一方面，`run_server.py` 当前没有相同的 `--conf` 入口。客户端 YAML 里的配置不会自动改变服务端模型类型、推理线程数或 LingBot 的权重。新增服务参数时要明确由谁读取。

`run_web_client.py` 启动时还会尝试终止占用其网页端口的进程。测试迁移程序时应选定空闲端口，或者把入口改为清楚报端口占用，避免无意关闭原来的运行实例。

依据：[Web 启动入口](../run_web_client.py)、[YAML 读取](../web_client/server.py:1134)、[机器人进程创建](../client/robots/robot_proxy.py:439)、[本机环境脚本](/home/bjtc/Sophix/g1/g1_pc_gdk_env.sh)。

### 7.3 可选的离线对照配置 不代表要替换 Open-RAIL 默认调度

正常迁移可以继续用 Open-RAIL 的异步调度和已有动作处理，只核对模型原始时间间隔、夹爪策略和等待上限。下面另列一份**可选的离线对照草案**，用于查看不做拟合时的原始目标；不是推荐把正式迁移改回串行，也不是已验收的上机配置。新适配器和夹爪任务规则仍需实现。

```yaml
rdm:
  mode: sync                     # 先一段一段比较，后续再测试边做边算
controller:
  raw_fps: 30                    # 模型动作相邻时间点的间隔依据
  speed: 1.0                     # 不加速播放模型计划
  period: 33.3333333333          # raw 模式每次取一个原始目标，单位毫秒
  gripper_offset: 0              # 不提前或推迟夹爪动作
intra_chunk:
  intra_chunk_mode: raw          # 第一轮对照保留模型原始目标
inter_chunk:
  inter_chunk_mode: sync         # 此处表示直接采用新段，不额外连接曲线
vision:
  history_frame: false
  preprocess:
    method: none                # 先只保留 LingBot 自己的图像预处理
robots:
  type: agibot_g1
  agibot_g1:
    hand_type: gripper
    gripper_freq: 1              # 每次实际控制调用都发送夹爪
language:
  file_path: lingbot_package_language.json
  task_id: package_a2d
  sub_task_id: 0
  auto_mode: false
record:
  switch: false
  lerobot:
    state_shape: 20             # 本草案保留机器人侧头腰状态
    action_shape: 16            # 模型只控制双臂和双夹爪
```

这里两个 `sync` 属于不同模块：第一个决定等这段结束再算下一段，第二个决定不额外修改两段之间的目标。不要把它们理解成一个总开关。

现有首次索引行为和“执行前 N 个”的差别仍需处理。上面配置只是减少比较中的额外变化，不能保证与旧 `g1` 逐条命令完全相同。

任务文件可按现有 JSON 结构定义：

```json
{
  "package_a2d": [
    "Pick a soft package from the box, orient its label upward, and place it on the conveyor belt."
  ]
}
```

当前本地 `default_conf.yaml` 选的是 `tea_master`，并包含原先的拟合、夹爪偏移和记录形状；不能把它直接当成 LingBot 软包配置。新配置还应核对机器人姿态预设，网页“复位”会使用这些值，不能沿用不适合当前场地的默认姿态。

### 7.4 模型服务的 50 与 25 必须明确区分

使用当前 50 步模型时，继续采用 `deploy.lingbot_vla_policy`，显式传 `--use_length 50`、对应权重与 `--norm_path`，并保留原部署使用的 `QWEN25_PATH`。它的命令行默认返回长度是 25，不能因为“这是 50 步模型入口”就省略参数；若直接构造 `LingbotVLAServer`，构造函数的 `use_length` 默认甚至是 1，也应显式设置。

真正的 25 步模型应使用已有 `deploy.lingbot_vla_policy_chunk25`。它还修正模型和数据配置中的 `chunk_size`，不是简单把 50 步结果截成 25 步。对应统计文件也要匹配。

Open-RAIL 的动作处理按收到的数组长度工作，没有要求所有模型一律返回 50 步。但接入适配器应严格验证所选配置，25 步计划可覆盖的未来时间更短，也要重新评估推理耗时。

方案 A 启动顺序为：准备机器人环境；启动并预热 LingBot；启动新增桥接服务；启动仅观察/推理的客户端；检查完成后再启用执行。新增桥接服务的预期命令形式如下，**注册代码完成后才可使用**：

```bash
python run_server.py --model_type lingbot_vla --model_path /实际使用的模型目录
```

地址、动作长度和等待上限等参数，应通过新增配置或已实现的命令行选项传入；本报告没有虚构一个当前就能运行的 `--lingbot-*` 参数集。

## 8 已有暂停和记录怎样复用 哪些差异需要另行说明

### 8.1 机器人状态检查属于任务适配 不属于重做调度

旧部署在执行中检查关节反馈是否过旧、整机错误、急停和双臂控制状态。Open-RAIL 当前 G1 的 `control_robot()` 主要拆分目标并发送，没有完整复用这些检查。

若迁移要求保留原 g1 的这组检查，应抽取 `_fresh()`、`_status_is_safe()`、`_check_live_status()` 的职责，在机器人实际发送前调用。不要直接导入整个旧部署脚本，因为其模块顶层还检查环境并导入其他任务依赖。这里迁移的是当前机器的检查规则，不是重新开发 Open-RAIL 的定时器或暂停功能。

同样，Open-RAIL 已有相机与状态的最近时间配对。若需要严格限制各路时差，再保留它目前丢弃的部分时间戳并增加检查；这是观测质量的增强，不是说它没有观测配对功能。

### 8.2 暂停直接使用现有机制 先明确实际效果

Open-RAIL 已经提供 `stop_control()`、`pause_controls()`：暂停提交新目标，更新内部控制版本号，并清理旧队列。机器人工作进程在调用 SDK 前检查版本，拒绝暂停前尚未开始执行的目标。**这套功能直接复用，不需要因为换 LingBot 而重写。**

它解决的是“客户端不再继续发送旧计划”。如果另外要求暂停按钮同时调用厂家的 `set_motion_stop()`，那是增加一个具体的机器人动作，需要单独接入，并验证如何恢复。已经被机器人接收的目标也不能靠清理电脑队列撤回。报告不把这项额外行为作为“Open-RAIL 没有暂停”的证据。

启动时也应按已有接口区别观察、推理与执行。旧 g1 默认 dry-run；Open-RAIL 的 `VLAClient.start()` 会同时启动推理和控制。可使用框架已有的独立启停接口进行仅推理验证，不要求先新增整套控制开关。

依据：[控制启停](../client/core/vla_client.py:189)、[暂停与旧队列失效](../client/robots/robot_proxy.py:631)、[客户端整体启动](../client/core/vla_client.py:235)。

### 8.3 记录系统直接复用 先改任务对应的格式配置

Open-RAIL 已有图像、状态、动作和实验数据保存机制。首版使用现有记录器，在任务 YAML 中设置保存目录、图像配置、状态与动作长度即可；不需要复制 `g1_rollout_recorder.py`，也不要求修改两个核心记录模块。

当前默认 `state_shape=20`、`action_shape=22`，写入器对短动作会补零。本报告推荐保留完整 20 维状态，模型控制动作设为 16 维，防止把补零误解为模型对头腰等部位的输出。若后续要生成原任务的训练数据，再明确抽取前 16 维状态和映射三路图像名称。

另有一个**可选的诊断需求**：现有客户端记录的是提交给 `RobotProxy` 的处理后目标，后面工作进程可能合并目标，RobotBody 还可能替换夹爪数值。若需要精确追踪“实际哪次调用 SDK、传了什么参数”，才需要在工作进程增加记录。现有记录不是不能用，只是不能把这一层目标直接标成硬件确认收到的命令。

依据：[提交目标与记录](../client/core/vla_client.py:553)、[记录补零逻辑](../client/core/lerobot_dataset_recorder.py:1035)。

## 9 本次迁移的边界：哪些直接用 哪些确实要加

| 能力 | Open-RAIL 已经有什么 | 这次迁移实际要做什么 |
| --- | --- | --- |
| 超时 | 等待模型响应有上限，请求编号用于丢弃不匹配的迟到结果 | 配置适合 LingBot 的等待时间；若用 WebSocket 转发，给新增加的这段连接设置等待上限 |
| 发送节奏 | 独立控制定时器、动作存储与取点、同步/异步推理、动作处理 | 选择相互匹配的模型时间间隔、处理方式和发送周期；不迁移旧 g1 调度，不重写定时器 |
| 暂停 | 停止提交、废弃旧控制版本、清理队列 | 直接复用，并验证当前 G1 的实际响应；只有额外要求厂家停止指令时才扩展 |
| 记录 | 数据记录管理、独立写入、图像与状态动作保存 | 修改本任务形状和目录配置；只有需要 SDK 级逐次诊断时才扩展字段和采集位置 |
| LingBot 模型接入 | 有统一模型适配接口，但没有 LingBot 实现 | 新增适配类和注册，转换字段，初始化模型，校验输入输出 |
| 当前软包夹爪规则 | 有通用夹爪控制，但行为与旧任务不同 | 保持左夹爪，明确右夹爪数值处理和发送间隔 |

因此本次的工作重点是**新增模型接入、处理任务语义差异、配置并验证已有能力**。不是先把 Open-RAIL 改造成旧 g1，也不是先完成一轮通用框架重构。

模型服务维持普通推理，启动时可显式指定 `--rtc-mode off`。本报告不包含模型侧 RTC 的协议、状态保存或调度修改。

## 10 推荐的实施顺序与验收内容

### 第一步：固定原部署的参照条件

记录使用的模型权重、统计文件、`package_a2d.yaml`、任务文本、三路图像样本和原始模型输入输出。选择 50 步还是 25 步，并明确旧程序每轮执行多少个目标。不要同时换模型权重、提示词、执行方式和图像格式。

这里“固定”指保存版本与参数供比较，不要求复制大量模型文件到 Open-RAIL。

### 第二步：只接模型 不接机器人运动

完成第 4.1 节的注册与适配。先用假 LingBot 服务验证通信，再使用保存的观测请求真实模型。

必须验证：reset 在第一次推理前完成；输入字段和顺序正确；输出形状与数值正确；时间字段不变；请求编号匹配；断线和超时能结束；同一连接不会并发接收。

如要比较模型输出，应控制随机数或先将同一份保存的输出用于两条执行链。扩散模型可能存在采样差异，不能将不同随机样本的差别都归为迁移错误。

### 第三步：只接机器人观测 对照模型入口图像

启用 RobotBody 读取，禁止发送 SDK 运动命令。核对关节 14 维、夹爪原始范围、完整状态中头腰的位置、图像时间与颜色。

把原部署和迁移后的模型输入分别保存，解释每项差异。不要仅凭网页图像看起来正常就跳过这一步。

### 第四步：用假 SDK 对照最终命令

输入相同模型动作，记录最终 `move_arm()`、`move_gripper()` 的实参和模拟发送时刻。

适配验收重点包括：左夹爪预测明显变化但最终保持不变；右夹爪数值符合所选策略；夹爪发送间隔符合配置；无头腰底盘自动命令；异常模型输出被拒绝。另检查现有发送、暂停和恢复机制在新链路上的表现。若发现首点索引或断线后末点保持的问题，单独记录为框架问题并判断是否阻碍部署，不将其笼统描述成“没有发送节奏或暂停功能”。

这一步比仅检查 `pred_action` 数组更重要，因为最容易出错的变化发生在模型结果返回之后。

### 第五步：在相同任务下做分阶段实机比较

先确认首次目标与当前姿态的差距及停止流程，再按现场已有流程验证短段动作。正式迁移可以直接采用 Open-RAIL 已有异步执行与动作处理；为定位差异，另做同步或关闭处理的对照实验即可，不要求先开发新调度。

每次只加入一种主要变化，记录发送间隔、两段之间的等待、实际跟随误差、抓取成功率和任务耗时。数据保存开关也单独比较，确认录制没有拖慢执行。

没有这些结果，只能说“已接入 LingBot”，不能说“已证明 Open-RAIL 更流畅”。

### 第六步：根据实测结果决定是否需要进一步优化

基础迁移完成后，如果新增通信确实成为瓶颈，再考虑从方案 A 改为方案 B。SDK 级诊断记录、无损图像传输和通用异常治理，也按具体问题决定是否实施，不作为本次迁移必须完成的额外项目。
