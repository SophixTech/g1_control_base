# 传送带红点检测与自动暂停/恢复方案

## 结论

建议在 **OpenRAIL 客户端**增加可选的 `conveyor_gate` 功能，不修改模型、训练或机器人 SDK。总体复杂度 **中等**：红色识别较简单，主要工作是协调暂停/恢复、清理旧动作和人工 Stop。

现有代码支持普通暂停/恢复，但不能直接套用全局 `pause()`：它会停止相机观察，导致暂停后无法检测红点。已有 `_control_failed` 故障锁存也不是普通暂停，红点恢复不能自动清除这种故障。

本方案将需求第（3）条理解为：**可见红点 ≥3 个允许工作；可见红点 <3 个持续存在时，继续工作 n 秒后暂停。**

## 运行流程

1. **Control Start**：启用检测，保留相机观察与预览；首次确认 ≥3 个点可见后，开始推理和执行。若启动时不可见，直接等待，不先运动 n 秒。
2. **工作中少于 3 个点可见**：启动一次 n 秒倒计时，期间继续推理和执行。连续缺点不会反复重置倒计时；若红点恢复则取消倒计时。
3. **倒计时结束**：先停止下发动作、清空待执行队列，再暂停推理；观察、红点检测和预览继续运行。这里是软件暂停，不是硬件急停。
4. **等待中恢复 ≥3 个点**：连续稳定满足条件后，使用暂停之后的新观测重新推理；拿到新动作块后恢复执行。不继续播放暂停前的旧 chunk，也不重置任务/子任务进度。
5. **人工 Control Stop / 全局 Pause / Reset / Observe Stop**：取消本轮自动运行授权及倒计时，红点出现也不能自行恢复；需要人工再次 Control Start。控制故障同样取消自动运行，不通过红点逻辑清除错误。

建议恢复条件连续满足约 0.5 秒，避免红点在阈值附近闪烁时频繁切换。相机反馈过期时转为暂停等待，不把旧帧一直当成“红点可见”。所有恢复操作在最后下发前再次确认人工授权，避免 Stop 与检测线程竞争。

**需确认的物理假设：**“≥3 点可见”必须能够代表传送台已回到工作位置；如果移动途中也能看到这些点，仅靠数量不足以证明归位。固定 ROI 可以减少这种误判，实测后再调整位置和稳定时间。n 秒只是时间规则，并不能证明包裹已经放好。

## 红点识别与配置

从机器人**原始头部图像**提取 5 个固定 ROI，不使用模型 mask 或 crop 后的图像。参考分辨率为 1280×800；同视野等比例分辨率可缩放 ROI，头部视角改变后需重新标定。

每个 ROI 使用 HSV 两段红色范围（色相靠近 0 和 180），结合饱和度/亮度下限；简单开运算去除噪点，最大红色连通区域面积达到阈值即算可见。相比只数所有红像素，连通区域可以减少零散红噪点影响。每个 ROI 最多算一个点。

配置示例（ROI 暂留空；未配置完整 5 个 ROI 时不允许开启自动控制）：

```yaml
conveyor_gate:
  enabled: false
  camera: cam.head
  reference_size: [1280, 800]  # 宽、高
  rois: []                   # 填 5 组 [x, y, width, height]
  min_visible: 3
  stop_delay_s: 2.0          # 示例 n，需要实测选择
  resume_stable_s: 0.5
  detect_hz: 10
  frame_timeout_s: 0.5
  hsv_red_ranges: [[0, 10], [170, 179]]
  saturation_min: 100
  value_min: 60
  min_blob_area_px: 20       # 示例阈值，标定后调整
```

检测始终使用最新帧，处理速度不足时跳过旧帧，不积压图像。默认关闭，原部署行为保持原样。第一版只通过 YAML 配 ROI 和阈值，不增加鼠标框选编辑器。

## 前端展示

在原有三路相机之外新增“传送带检测”面板，显示：

- 5 张 ROI 小图（可拼成一张 JPEG），各自标注可见/不可见、红色区域面积。
- 可见数量，例如 `3/5`。
- 状态：未启用、等待归位、运行、延迟停止、人工停止/故障；倒计时显示剩余秒数。

面板以约 5–10 Hz 更新，原有三路相机编号不变，检测图不进入模型输入或训练录制。自动等待时按钮仍显示 **Control Stop**，因为自动运行授权仍然有效；点击后才能明确取消自动恢复，不能依赖 `control_running` 单个布尔值决定按钮动作。

## 修改位置

| 文件 | 修改内容 |
|---|---|
| 新增 `client/core/conveyor_gate.py` | HSV/连通区域识别、5 个 ROI、延迟及稳定计时、状态转换；输出检测结果和预览 |
| `conf/client_conf.py`、`conf/*.yaml` | 添加默认关闭的配置项，ROI 先留空 |
| `client/core/vla_client.py` | 从原始头部图像接入检测；区分人工运行授权和实际控制状态；调度暂停、恢复，并纳入 `runtime_status` |
| `client/core/realtime_data_manager.py` | 清理旧动作/融合轨迹；以暂停代次标记或等效机制拒绝暂停前仍在途的推理结果，恢复必须等待新观测生成的新 chunk |
| `client/robots/robot_proxy.py` | 复用暂停队列和 epoch 机制；将故障状态持续传回上层，阻止显示运行但实际丢弃动作；不自动清除故障 |
| `web_client/server.py` | Start/Stop 按人工授权切换；协调 Reset/Pause；通过 WebSocket 发布检测状态与 ROI 拼图 |
| `web_client/static/index.html`、`modules/camera.js`、`modules/websocket.js` 及相关样式 | 增加检测面板，接收独立检测消息，不挤占三路相机 |
| `tests/test_conveyor_gate.py`（新增） | 离线检测和状态机测试；模拟在途推理、Stop 与自动恢复竞争 |

新状态机只调用现有控制接口，不重写轨迹插值。初次 Start 与自动恢复分开处理，避免现有 `start_control()` 中的 `new_task()` 重置子任务进度。推理结果的清理与接受须和现有推理锁协调，不能只改几个线程开关。

## 实现顺序与复杂度

1. **检测与预览**：先实现 ROI 配置、离线识别、5 图面板，只观察不接管动作。复杂度低至中。
2. **自动暂停/恢复**：接入状态机、清旧 chunk、人工 Stop 优先及故障状态。复杂度中，为主要工作量。
3. **现场标定**：配置 5 个 ROI，测试包裹遮挡、光照、传送台移动途中及归位，选择 n 和阈值。复杂度取决于画面稳定性。

粗估编码与离线测试 2–3 个工作日，现场标定/联调另约半天至一天；不含硬件改造或复杂识别模型。验收至少覆盖：≥3 点运行、<3 点延迟一次后暂停、恢复只用新动作、人工 Stop 后不自动恢复、控制故障后不自动恢复。暂不需要深度学习检测器或完整工作流引擎。

本次仅提出方案，未修改运行代码或启动机器人。

## 实现说明（2026-10-24）

已实现可选功能，使用说明见根目录 `README-Conveyor-Gate.md`。实际配置放在 `vision.conveyor_gate`，遵循现有配置分组；前端采用独立 GET 接口约 5 Hz 拉取检测状态/ROI 拼图，保持三路相机传输不变。控制协调拆分到 `conveyor_control.py`，复用现有推理锁、RDM.clear 和机器人队列 epoch，不重写轨迹插值。等待在途推理结束后再清理结果，恢复只接受清理之后的新观察与动作。
