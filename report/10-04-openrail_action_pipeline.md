# Open-RAIL 为什么会下发与模型预测不同的关节角度

分析对象：G1 真机上的 LingBot-VLA 部署、2026-10-03 的两份关节日志，以及 G1 仓库的串行部署代码。本文于 2026-10-04 更新，补充了后续数值重建结果。

**主要结论：模型只给出一串目标位置。Open-RAIL 会根据这些位置计算速度、加速度，再结合旧规划，重新生成一条过渡曲线。日志中的大幅目标偏离主要出现在这一步。**例如模型整块预测在 −0.393～−0.376 rad，客户端生成并交给 SDK 的目标却到达了 −1.458 rad。

下面先解释每一步做什么，再用这个案例说明偏离如何产生。这里的“目标到达 −1.458”指软件下发这个角度，**不等于电机实际转到了这个角度**。

## 1. 先分清模型输出、规划目标和真机反馈

假设模型希望右臂某个关节接下来依次到达 −0.40、−0.39、−0.38 rad。它给出的就是一串位置。rad 是弧度，1 rad 约为 57.3°。

本次 LingBot 每次返回 50 行，每行 16 个数：前 14 个是左右臂关节角度，最后 2 个是夹爪值。这 50 行合起来叫一个 **action chunk**，也就是“一次推理得到的一段动作预测”。每一行叫一个 action。下文的 chunk 55 是某次请求的编号，不是第 55 个关节或第 55 帧。

| 本文用词 | 具体是什么 | 谁产生的 |
|---|---|---|
| 模型目标 | 模型这次返回的 50 行位置 | LingBot 的部署 policy |
| 插值目标 | 在这 50 行之间补出的更密集的位置点 | 客户端插值程序 |
| 融合后目标／规划目标 | 为衔接新旧预测而重新计算的位置点 | 客户端跨块融合程序 |
| 提交目标 | 控制线程交给机器人代理的位置 | 客户端控制线程 |
| SDK 下发目标 | 调用 `move_arm()` 时传入的位置 | G1 适配器 |
| 反馈位置 | 从机器人读回来的关节角度 | 机器人状态接口 |

模型部署 policy 已经把模型内部的归一化结果还原成关节角度。例如 −0.4 表示“目标角度为 −0.4 rad”，不是“在当前角度上再减 0.4”。Open-RAIL 的 LingBot 适配器没有再次叠加当前状态，也没有把角度乘以 speed。

**模型没有输出速度和加速度。本文出现的规划速度、规划加速度，都是客户端从位置序列计算的，也不是机器人实测值。**

## 2. 从一次观测到一次下发，中间发生了什么

这里的“观测”就是交给模型的相机图像、关节状态和任务文字。“推理”就是让模型根据这份观测生成下一段预测。

```text
读取图像和关节状态
    ↓
模型返回 50 行目标位置
    ↓
客户端规定每行位置应该安排在什么时候
    ↓
在原始位置之间补点，并计算位置变化的速度、加速度
    ↓
根据观测已经过去多久，选择新预测从哪里接入
    ↓
用旧规划的位置、速度、加速度，生成连接新预测的过渡曲线
    ↓
每隔约 3.75 毫秒取一个目标，提交给机器人代理
    ↓
G1 适配器调用 move_arm()，把 14 个关节位置交给 SDK
```

这几个组件各有明确职责，不需要先记住类名：

| 代码中的名字 | 在这条流程里负责什么 |
|---|---|
| `VLAClient` | 组织观测、请求模型、调用后续处理，并定时提交动作 |
| `RealtimeDataManager`，简称 RDM | 保存最新观测和轨迹，并记住当前执行到第几个点 |
| `IntraChunkSmoother` | 处理一块内部：把模型的稀疏位置补成密集位置 |
| `InterChunkFuser` | 处理两块之间：生成从旧规划接到新预测的过渡 |
| `RobotProxy` | 把控制请求送到运行机器人接口的子进程 |
| G1 `body_robot.py` | 检查状态，并调用 SDK 的手臂、夹爪接口 |

ZMQ 是客户端与模型服务之间的消息传输工具。每次请求带一个编号 `request_id`，客户端只接受匹配的响应，避免用错旧响应；ZMQ 本身不负责插值或放大角度。

## 3. 30 Hz 和约 267 Hz 为什么同时存在

### 3.1 raw_fps 和 speed 决定原始位置之间隔多久

当前配置中的 `raw_fps=30` 表示按每秒 30 个原始动作点解释模型输出。`speed` 用来调整这串动作的播放时间。

例如模型返回三个位置，speed 为 1 时，客户端给它们安排的时间是：

| 原始点编号，从 0 开始 | 示例目标 rad | speed=1 的时间 | speed=0.5 的时间 |
|---:|---:|---:|---:|
| 0 | −0.40 | 0 秒 | 0 秒 |
| 1 | −0.39 | 0.0333 秒 | 0.0667 秒 |
| 2 | −0.38 | 0.0667 秒 | 0.1333 秒 |

**speed 减半时，位置数值没有减半；是到达相邻原始位置的时间间隔加倍了。**这些时间以本块原始第 0 点为零点，不是电脑的日期时间。

计算方法是：

```text
原始相邻点间隔 = 1 / (raw_fps × speed)
整块第一个点到最后一个点的时长 = (原始点数 − 1) × 相邻点间隔
```

50 个点之间有 49 个间隔：

| speed | 相邻原始点间隔 | 50 点首末时长 |
|---:|---:|---:|
| 1.0 | 33.33 毫秒 | 1.633 秒 |
| 0.5 | 66.67 毫秒 | 3.267 秒 |
| 0.3 | 111.11 毫秒 | 5.444 秒 |

所以“按 raw_fps 和 speed 生成时间轴”的具体意思就是：**给模型返回的每一行位置标注一个计划执行时间。**修改 speed 影响后续生成的轨迹，不会立即重新计算已经发布的旧轨迹。

### 3.2 controller.period 决定多久取一次下发目标

另一个参数 `controller.period=3.75` 的单位是毫秒。客户端使用这个周期补点和运行控制回调：

```text
原始模型点：0、66.67、133.33……毫秒     （speed=0.5）
补点后的点：0、3.75、7.50、11.25……毫秒
```

客户端用三次样条 `CubicSpline` 画一条经过原始点的位置曲线，再从曲线上每隔 3.75 毫秒取一个位置。50 个原始点因此可能变成几百个下发目标；chunk 55 是 872 个补点后的目标。

计划下发频率为 `1000 / 3.75 ≈ 267 Hz`。两份日志中，策略 SDK 调用间隔中位数约 3.81 毫秒，对应约 262 Hz。这里排除了不少于 100 毫秒的间隔。

**这不是把原始动作加速约 9 倍，而是在相同的计划时间内多补一些位置点。**267 Hz 也不是模型每秒推理次数，更不是已经测得的机器人内部伺服频率。

源码入口：[控制周期与回调](../client/core/vla_client.py)、[定时器](../client/utils/multi_thread_timer.py)、[补点程序](../client/core/intra_chunk_smoother.py)。

## 4. 模型只预测位置，速度和加速度从哪里来

客户端会计算两次导数。第一次是对模型位置做三次插值后求导；第二次是新旧块融合后，对已经改写的位置重新做差分。这两组导数来源不同，不能混为一谈。

### 4.1 第一次：把位置画成曲线，再求曲线的导数

对一个关节，模型只返回 `q_raw[0]` 到 `q_raw[49]`。客户端先按第 3 节给每个位置安排时间，再用 `CubicSpline` 连成曲线。

“三次样条”不是用一条三次多项式拟合整块，而是在相邻原始点之间分别使用三次多项式，并让这些小曲线在接缝处连接平滑。默认边界条件也会影响首尾曲线的形状。它经过原始位置点，因此不等于过滤掉原始位置中的波动。

在某一个小区间里，可以把位置写成：

```text
s = 从这个小区间起点算起的秒数
q(s) = c0 + c1×s + c2×s² + c3×s³
v(s) = c1 + 2×c2×s + 3×c3×s²
 a(s) = 2×c2 + 6×c3×s
```

`c0～c3` 是插值程序根据位置点求出的系数；`v` 是位置对时间的一阶导数，`a` 是二阶导数。单位分别为 rad、rad/s、rad/s²。

举一个只用于解释求导的例子，假设某段曲线是：

```text
q(s) = −0.4 + 0.2s − 0.05s² + 0.01s³
```

那么在 `s=0.1 秒`：

```text
位置 q = −0.38049 rad
速度 v = 0.2 − 0.1×0.1 + 0.03×0.1² = 0.1903 rad/s
加速度 a = −0.1 + 0.06×0.1 = −0.094 rad/s²
```

代码不需要手工写出系数，SciPy 直接返回这些值：

```python
cubic_spline = CubicSpline(timestamps, action_chunk[j])
position = cubic_spline(timestamps_fitted)         # 曲线上的位置
velocity = cubic_spline(timestamps_fitted, 1)      # 一阶导数
acceleration = cubic_spline(timestamps_fitted, 2)  # 二阶导数
```

这里 `j` 表示正在处理的关节，`timestamps` 是 50 个原始点的时间，`timestamps_fitted` 是每隔 3.75 毫秒取一次的密集时间。

**模型没有提供这些速度和加速度。它们由位置变化、客户端安排的时间和插值方法共同决定。**位置小幅来回变化，也可能产生较大的二阶导数。

### 4.2 第二次：融合改写位置后，按相邻点重新计算

跨块融合会重新生成位置曲线，因此旧的导数不再适用于这段新位置。当前代码没有在这里直接求五次曲线的解析导数，而是使用差分：

```text
δ = 相邻密集点的时间间隔，本例 0.00375 秒
v[i] = (q[i] − q[i−1]) / δ
 a[i] = (v[i] − v[i−1]) / δ
```

例如相邻位置从 `−0.400` 变成 `−0.39925 rad`，则速度为：

```text
(−0.39925 − (−0.400)) / 0.00375 = +0.2 rad/s
```

如果上一点速度为 `+0.19 rad/s`，本点加速度就是：

```text
(0.2 − 0.19) / 0.00375 ≈ +2.667 rad/s²
```

融合后算出的 `q、v、a` 一起存入 RDM。下一块到来时，“旧规划速度和加速度”就从这里取。第 6.8 节会用真实日志演示边界处怎样计算。

SDK 的 `move_arm()` 仍然只接收位置。**这些导数的作用是参与下一次轨迹生成，间接改变以后下发的位置，不是直接作为电机速度或加速度指令发送。**

## 5. 异步执行时，新预测怎样替换旧预测

### 5.1 新预测返回时，机器人还在执行上一段

当前 `rdm.mode=async` 表示“推理与控制同时进行”：模型计算新块时，控制线程继续取旧轨迹的点。不是同时向模型无限提交多个请求。

```text
推理线程：计算 A → 发布 A → 计算 B → 发布 B → 计算 C……
控制线程：执行旧轨迹      → 执行 A 的一部分 → 执行 B 的一部分……
```

每次推理和处理结束后，线程只额外等待配置的 10 毫秒，就继续请求下一块，不等旧块执行完。日志中一次请求到响应通常约半秒，因此很多块只下发了约半秒就被下一块替换。

### 5.2 客户端会跳过新预测中已经“来不及”的前段

例如从打包观测到开始融合已经过去 0.5 秒，程序通常从新预测中第一个计划时间大于 0.5 秒的点附近接入，不再从第 0 点执行。这就是原文所说的“按观测年龄选起点”。

这里的计时从客户端打包观测开始，不是从相机曝光开始。它包括后续编码、等待、请求、模型计算和补点所用的时间，但不包含之后的融合计算、队列和设备执行延迟。

**时间对齐不等于状态对齐。**跳到预测的 0.5 秒处，并不能保证机器人实际已经走到模型预期的那个位置。

### 5.3 融合器读取的是旧规划，不是真机反馈

程序从旧轨迹当前执行索引处取出位置、速度、加速度，作为新过渡的起点。`get_current_state()` 这个名字容易误导：这里的 state 是旧规划状态，不是刚读到的机器人反馈。

所以新模型可能根据真机反馈预测“保持在 −0.38 附近”，融合器却从旧规划的“−1.37，而且还在向更负方向走”开始接续。两者的出发点不同。

首次推理或只开推理、未开控制时，没有使用这组旧状态，通常不生成这种跨块过渡。因此只看未启动控制时的可视化，不能代表真正执行时的轨迹。

## 6. 按真实日志一步步计算 min_jerk 衔接

本节讲的是当前代码中实际启用的 `_min_jerk_chunk_transition_numpy()`，不是对论文算法的逐字复述。它使用一段五次曲线和尾部混合；论文正文描述的双段五次构造与此不同。

先回答“从前一块哪里连接到后一块哪里”：

> **从读取旧状态时，旧块正在执行的那个规划点出发；连接到新块延迟接入点之后的某个远期点。它不是默认连接旧块末点与新块首点，也不是直接连接新块的延迟接入点。**

下面只看右臂第二关节，即全局索引 8，使用 19:15 会话的 chunk 54 → 55。所有数组索引从 0 开始。

### 6.1 先分清三个点和两种编号

这里有三个位于不同数组中的点：

| 符号 | 表示什么 | chunk 54 → 55 的值 |
|---|---|---:|
| `i_old` | 读取旧状态时，旧块当前执行到的密集点索引 | 旧块 54 的 281 |
| `k` | 新块按延迟选择的密集接入索引 | 新块 55 的 142 |
| `e` | 新块中作为过渡终点的密集索引 | 新块 55 的 871 |

**281、142、871 都是插值后数组的索引，不是 50 个原始模型点的编号。**例如新块索引 142 对应 `142×0.00375=0.5325 秒`，大约位于原始第 7 与第 8 点之间。

```text
旧块 54 的已融合轨迹：
…… → [281：读取 q、v、a 作为起点] → [282：融合计算期间又提交了这一点]
                                               后续剩余旧轨迹被替换

新块 55 融合之前的插值轨迹：
[0 …… 141] [142：按延迟选出的接入点] …… [871：选中的过渡终点]
   通常跳过       用于比较新旧差异                  提供终点 q、v、a

新块 55 融合之后存储的轨迹：
[0 …… 141] [142：写入旧块 281 的位置] → 五次过渡曲线 → [871：新预测终点]
                    下一次通常从 143 开始提交
```

旧块 281 的时间和新块 142 的时间分别相对于各自原始第 0 点计时。不能直接把 `281−142` 当成跨块经过了多少时间。

### 6.2 第一步：准备新块的密集位置、速度和加速度

chunk 55 返回 50 个原始点，`raw_fps=30`、`speed=0.5`，所以原始点间隔为：

```text
Δraw = 1 / (30×0.5) = 0.0666667 秒
原始点时间 = 0、0.0666667、0.1333333……3.2666667 秒
```

按第 4.1 节做三次插值和求导，再每隔 `δ=0.00375 秒`取值，得到三组数组：

```text
Q_new[n]：第 n 个密集点的位置
V_new[n]：同一个点的插值速度
A_new[n]：同一个点的插值加速度
```

这些数组各有 `N=872` 个点，索引为 0～871。最后一个密集点时间是 `871×0.00375=3.26625 秒`，略早于原始最后一个点；这是 `np.arange` 取样的结果。

### 6.3 第二步：根据观测延迟，选新块的 k

程序计算“开始融合的 PC 时间减去打包观测的 PC 时间”，再找第一个计划时间晚于这个差值的密集点。

本例 `k=142`，对应新块时间 0.5325 秒。因此按当前索引规则，选点时的观测已用时间在约 0.52875～0.5325 秒之间；日志没有直接记录精确的融合起始时间，这个区间是由索引推出来的。

新块融合前在这个位置的值是：

```text
Q_new[142] = −0.381246830 rad
V_new[142] = −0.013272067 rad/s
A_new[142] = +0.082289534 rad/s²
```

**k 的作用是确定从新数组的哪里开始改写，并比较新旧差异。k 处的新模型位置并不是本例过渡的最终目标。**

### 6.4 第三步：从旧块当前索引取起始条件

`get_current_state()` 在读取时取到旧块索引 `i_old`，再从旧的已融合数组取出三项。本例重建匹配到 chunk 54 的密集索引 281：

```text
q0 = Q_old[281] = −1.372323219 rad
v0 = V_old[281] = −0.435014141 rad/s
 a0 = A_old[281] = +0.857067487 rad/s²
```

注意：`Q_old` 不是 chunk 54 原始模型预测，而是 chunk 54 经过之前融合后的规划。旧导数也来自之前的差分重算，不是机器人反馈。

融合计算期间控制线程还能继续前进，所以旧块 282 也被提交了；这解释了为什么新过渡起点不一定等于切换前最后一条提交值。此处旧状态是通过日志反推、与旧提交点匹配确认的，没有直接记录完整融合输入。

### 6.5 第四步：决定过渡要多长，以及终点在哪里

这里用 `r` 表示“过渡比例”。前文曾将它写成 α；它不是论文中表示执行加速倍率的 α。

当前 `adaptive_factor=-1`，表示让程序自动计算 `r`：

```text
Dq = 新块 k 点与旧状态之间的位置差大小
Dv = 新块 k 点与旧状态之间的速度差大小
Da = 新块 k 点与旧状态之间的加速度差大小

r = min(1, 0.25 + 1.0×Dq + 0.75×Dv + 0.15×Da)
```

这里的“差大小”实际使用全部 gradual 关节的欧氏范数。本次 gradual 关节就是 14 个手臂关节。例如 `Dq = sqrt(关节0位置差² + …… + 关节13位置差²)`。每个关节有自己的曲线，但它们共用这个过渡比例和长度。

本例只看关节 8，就有：

```text
位置差绝对值 ≈ 0.991076
速度差绝对值 ≈ 0.421742
加速度差绝对值 ≈ 0.774778

0.25 + 0.991076 + 0.75×0.421742 + 0.15×0.774778 ≈ 1.673600
```

全关节范数不小于其中一个关节的绝对差，因此即使没有其他关节日志，也能确认这里 `r=1`。若配置的 `adaptive_factor` 非负，代码改用该固定比例，并限制在 0～1。

然后依次计算：

```text
L = min(int(N×r), N−k) = min(872, 730) = 730 个点
T = L×δ = 730×0.00375 = 2.7375 秒
e = k+L−1 = 142+730−1 = 871
```

于是从新块的 **871 点**读取终点条件：

```text
qf = Q_new[871] = −0.388055000 rad
vf = V_new[871] = +0.010698713 rad/s
 af = A_new[871] = +0.528917388 rad/s²
```

因此本例真正连接的是：

```text
旧块已融合轨迹的 281 点 → 新块尚未融合轨迹的 871 点
```

只是这条连接曲线被写入了新数组的 **142～871** 区域。如果 `r` 较小，终点 `e` 就会位于新块中间，而不是末尾。如果 `L≤1`，函数不生成过渡。

实现有一个一周期差别：730 个点之间只有 729 个间隔，实际首末取样跨度为 `729×0.00375=2.73375 秒`，但公式使用 `T=2.7375 秒`。离线精确重建保留了这个差别；它不是本次大幅偏离的主要来源。

### 6.6 第五步：用六个边界条件生成五次曲线

`jerk` 是加速度的变化率，即位置的三阶导数。对于给定时长和起终点的位置、速度、加速度，标准的最小平方 jerk 插值问题会得到五次多项式。这里的函数直接使用这种五次插值的基函数，没有在线求解带关节限位、速度限制的优化问题；后续尾部混合和差分也意味着不能把最终实现简单等同于理想的最小 jerk 解。

为何需要五次？一个五次多项式有六个系数，可以满足六个端点条件：起点和终点各自的位置、速度、加速度。

程序先把过渡进度写成 0～1 之间的数。对于新数组中第 `n` 个点：

```text
τ = (n−k) / (L−1)

n=k 时 τ=0，表示过渡开始
n=e 时 τ=1，表示过渡结束
```

设以下六个函数都在同一个 τ 处计算：

```text
h0 = 1 − 10τ³ + 15τ⁴ − 6τ⁵
h1 = τ − 6τ³ + 8τ⁴ − 3τ⁵
h2 = (τ² − 3τ³ + 3τ⁴ − τ⁵) / 2
h3 = 10τ³ − 15τ⁴ + 6τ⁵
h4 = −4τ³ + 7τ⁴ − 3τ⁵
h5 = (τ³ − 2τ⁴ + τ⁵) / 2
```

该点的过渡位置为：

```text
Q_transition[n] = h0×q0 + h1×(v0×T) + h2×(a0×T²)
                + h3×qf + h4×(vf×T) + h5×(af×T²)
```

不要把这六项理解成六个目标位置的平均值。速度项乘 T、加速度项乘 T²，是为了把“每秒”的导数换到 0～1 的进度坐标；这些项会改变整条曲线的形状，没有保证中间位置落在 q0 与 qf 之间，更没有保证它位于模型预测范围内。

本例在 `n=240` 时：

```text
相对过渡起点的计划时间 = (240−142)×0.00375 = 0.3675 秒
τ = (240−142)/729 ≈ 0.134431
Q_transition[240] = −1.457636270 rad
```

它与日志一致。第 7.3 节给出了六项对这个数值的贡献。

### 6.7 第六步：过渡后 30% 再混入原始插值位置

在 `τ≤0.7` 时，直接使用上述五次曲线。超过 0.7 后，计算混合比例：

```text
β = (τ−0.7)/(1−0.7)
Q_out[n] = (1−β)×Q_transition[n] + β×Q_new[n]
```

例如 `τ=0.85` 时，β=0.5，取五次曲线与新块原始插值位置的各一半。这里的 `Q_new[n]` 是“同一个 n 处”的参考位置，不是一直与终点位置混合。

程序只改写 `k～e`。`k` 之前的数组元素仍保留原插值值，但常规换块不再执行它们；`e` 之后若有点，也保持原插值值。到 e 时回到新轨迹终点。

本例 `τ=0.7` 对应约 1.913625 秒，实际第一个进入尾部混合的采样点约在 1.91625 秒。新块在约 0.55 秒就被下一块替换，因此这一块的尾部混合没有被执行到。

### 6.8 第七步：根据最终位置重新计算导数

代码把 `Q_out` 的相邻点做差，重新生成后续融合要用的速度、加速度。第一个点没有前一点时，使用旧状态补齐：

```text
V_out[k] = (Q_out[k]−q0)/δ
A_out[k] = (V_out[k]−v0)/δ

对 n>k：
V_out[n] = (Q_out[n]−Q_out[n−1])/δ
A_out[n] = (V_out[n]−V_out[n−1])/δ
```

五次过渡首位置恰好等于 q0，所以 `V_out[k]=0`。这是当前实现的边界问题：起点位置连续，并不意味着真实运动速度为零，但这次差分算成了零。

代入本例得到：

| 新块密集索引 | 最终规划位置 rad | 重算速度 rad/s | 重算加速度 rad/s² |
|---:|---:|---:|---:|
| 142，融合边界，未作为本次首条指令下发 | −1.372323219 | 0 | +116.003771 |
| 143，首个实际提交点 | −1.373950693 | −0.433993127 | −115.731501 |
| 144，第二个实际提交点 | −1.375565940 | −0.430732473 | +0.869508 |

第一行由公式重建，后两行来自日志。例如：

```text
V_out[143] = (−1.373950693 − (−1.372323219))/0.00375 ≈ −0.433993
A_out[143] = (−0.433993 − 0)/0.00375 ≈ −115.7315
```

这些是软件导数尖峰，不是电机实测加速度，也不是直接发送的加速度命令。它们被保存后有机会参与后续融合，但本次日志没有显示下一块直接继承这些边界尖峰，详见第 7.4 节。

### 6.9 第八步：发布新数组，并从 k+1 开始提交

RDM 将新的位置、速度、加速度数组一起替换进去。对已经持续处于控制模式的普通换块，执行索引设为 k；控制回调先加 1 再取值，所以本例第一条是 143，不是 142。

本例提交了新块索引 **143～289，共 147 个点**，随后 chunk 56 接管。原计划要到 871 才完成本次过渡，实际没有走到那里。

chunk 56 读取的旧状态已经是 chunk 55 融合后索引 289 的状态：

```text
位置 −1.434018443 rad
速度 +0.250734227 rad/s
加速度 +1.331036863 rad/s²
```

于是下一轮重新执行本节步骤。对初次启动、从可视化切回控制等情况，代码可能把索引重置为 0，不能一律套用这里的 k+1；这些例外见附录 B。

### 6.10 把整个算法连起来看

下面是普通换块的教学伪代码。数组表示所有相关关节，省略夹爪与异常分支：

```python
# 1. 模型只给出位置；这里生成密集位置和导数。
Q_new, V_new, A_new, times = interpolate_and_differentiate(raw_positions)

# 2. 新块用已过去的时间选 k；旧块用当前执行索引选 i_old。
k = first_index_after_observation_age(times)
q0, v0, a0 = read_current_old_plan()

# 3. 用旧状态与新块 k 点的差异计算比例，决定远期终点 e。
r = compute_transition_ratio(q0, v0, a0, Q_new[:, k], V_new[:, k], A_new[:, k])
L = min(int(len(times) * r), len(times) - k)
T = L * control_period_seconds
e = k + L - 1

# 4. 从旧状态连接到新块 e 点，不是连接到新块 k 点。
Q_out = Q_new.copy()
Q_out[:, k:e+1] = quintic_and_tail_blend(
    q0, v0, a0, Q_new[:, e], V_new[:, e], A_new[:, e], T,
    original_segment=Q_new[:, k:e+1],
)

# 5. 最终位置用于下发，重算导数保存给下一轮融合。
V_out, A_out = finite_difference(Q_out, k, q0, v0)
publish_new_plan(Q_out, V_out, A_out, start_index=k)
# 控制回调随后先递增索引，再提交该点位置。
```

现在可以看出两个影响：一是改变 chunk 长度或 speed 会改变 N，进而影响过渡时长；二是新预测返回得快时，上一次过渡尚未完成就会重新规划。降低 speed 同时改变时间与导数，不能只根据公式的 T² 就推断偏差会怎样变化。

源码对照：[块内插值与求导](../client/core/intra_chunk_smoother.py)、[旧状态读取与索引推进](../client/core/realtime_data_manager.py)、[五次过渡和差分重算](../client/core/inter_chunk_fuser.py)。

## 7. 用日志解释 −0.38 为什么变成 −1.458

这里使用 19:15 会话的关节 8，即右臂第二个关节。我们用当前融合函数重建了 chunk 48～56 的已提交目标，逐点数值误差为 0。旧边界状态是从日志反推并匹配旧提交记录得到的，不是日志直接保存的完整融合参数。

### 7.1 偏离是逐块传下来的

| chunk 编号 | 模型整段角度范围 rad | 过渡起始位置 rad | 本块最后提交位置 rad |
|---:|---:|---:|---:|
| 52 | −0.394～−0.379 | −0.283 | −0.516 |
| 53 | −0.399～−0.380 | −0.516 | −1.037 |
| 54 | −0.399～−0.378 | −1.037 | −1.374 |
| 55 | −0.393～−0.376 | −1.372 | −1.434，期间最低 −1.458 |

chunk 55 起点略不同于上一块最后提交值，是因为匹配到的是上一块倒数第二个点。可以看到模型连续要求在 −0.38 附近，软件规划却不断向负方向偏离。

### 7.2 chunk 52 的远期末端加速度放大了当前偏离

该块最后五个原始位置约为：

```text
−0.385607、−0.392944、−0.391553、−0.383196、−0.390429 rad
```

位置幅度小，但方向来回变化。三次插值在融合终点处算出的加速度约为 **−9.363 rad/s²**。融合器用这个值作为约 2.72 秒长曲线的终点条件。

为了检查它的作用，我们保持其他输入和过渡时长不变，只把这个终点加速度设为零。这种“只改一个因素再比较”的离线计算，不是一次新的真机实验。

在融合开始后 0.495 秒，结果如下：

| 量 | 当前代码复现值 | 仅把新轨迹终点加速度设为零 |
|---|---:|---:|
| 位置 rad | −0.515643 | −0.375428 |
| 速度 rad/s | −0.847632 | −0.127839 |
| 加速度 rad/s² | −1.512117 | +0.451897 |

下一块实际继承的是左列：已经越过模型目标，仍快速向更负方向运动，而且还在往该方向加速。这里定位了一个明确的放大环节；chunk 52 之前就有偏离，不能说所有异常最初都由这一块产生。

### 7.3 chunk 55 的 −1.458 可以逐项算出来

这次过渡的起点是旧规划位置 −1.372323 rad、速度 −0.435014 rad/s、加速度 +0.857067 rad/s²。终点位置约 −0.388055 rad，过渡时长约 2.74 秒。

融合开始后 0.3675 秒，各项对位置的贡献是：

| 来源 | 位置贡献 rad |
|---|---:|
| 旧起始位置 | −1.345345 |
| 旧起始速度 | −0.145683 |
| 旧起始加速度 | +0.037635 |
| 新轨迹终点位置、速度和加速度合计 | −0.004243 |
| **相加后的目标** | **−1.457636** |

该时刻原始模型曲线约为 −0.383143 rad。当前过渡才走完约 13.4%，所以旧状态仍起主要作用。

这一次旧加速度为正，正在帮助减速。只清零旧加速度，结果反而变为 −1.495272 rad。因此不能把“所有加速度清零”当成已经验证的修复。

### 7.4 边界差分尖峰存在，但没有证据表明它在这些切换中逐块传递

新过渡首位置等于旧位置，差分会把首速度算成零。下一点又恢复运动速度，于是算出一个很大的加速度。例如 18:11 会话切入 chunk 48 后，首个提交点的规划加速度为 170.438 rad/s²，第二点立即回到 0.854 左右。

后续核查的 141 次连续切块中，反推起点全部匹配到旧块最后一个或倒数第二个提交点，最少也已离开旧块首个提交点 19 个采样步，没有匹配到那个边界尖峰点。

所以目前的结论是：**尖峰计算需要修，但日志更直接证明的是偏离位置和后续运动趋势被继承，不能把“尖峰逐块累积”当作已证实原因。**

## 9. 最终下发和 G1 串行路径有什么不同

生成的新轨迹会替换当前轨迹，而不是接在旧块后面排队。RDM 一起更新位置、导数和执行索引，避免控制线程读到一半新数据、一半旧数据。

控制定时器每次把索引加 1，再取一个位置点。RobotProxy 把它送到子进程；若有积压，子进程可能跳过中间请求，只处理最新请求。G1 适配器检查状态后，取前 14 个数调用 `move_arm()`，不再缩放手臂角度。

两份日志中，成功关联的提交目标与 SDK 目标完全相同。没有证据显示这一段把关节 8 的数值放大。日志也没有显示大量队列丢弃：A 没有明确丢弃，B 有一条。

| 环节 | G1 仓库串行执行 | 本次 Open-RAIL 配置 |
|---|---|---|
| 下发位置 | 直接取模型原始目标 | 补点后再用跨块曲线改写 |
| 执行节奏 | 原始点按 30 Hz 下发 | 密集点计划约 267 Hz，日志约 262 Hz |
| 下次观测推理 | 执行完选定前缀后开始 | 旧轨迹仍在执行时就开始 |
| 新块到达 | 上次选定前缀已执行完 | 立即替换旧块剩余部分 |
| 是否继承规划导数 | 没有本文这套 min_jerk 继承 | 有 |

“执行完一块”在 G1 代码中通常指执行完选定前缀，不一定执行模型返回的全部点。当前 50 帧脚本默认执行 30 帧，25 帧脚本默认执行 20 帧；历史测试应以当时启动参数为准。

因此，G1 较稳定不能只解释成“串行有停顿”。更重要的差别是它没有这套改写目标位置的融合过程。仅把 Open-RAIL 的 `rdm.mode` 改成 `sync`，也不会自动关闭插值、融合或延迟选点。

其他模型如 π0、GR00T、SmolVLA、ACT、RDT 等也把动作块交给这套客户端流程。相同配置下存在同类风险，但没有它们的运行日志，不能断定异常程度相同。

## 10. 目前应当先改什么

优先修改跨块融合，而不是先换模型或继续调低 speed。具体顺序是：

1. 用 chunk 52～55 的固定输入做离线回归对照，检查修改后的位置偏差、速度和加速度。
2. 将过渡与整个 chunk 的长度解耦，研究受约束的局部衔接；不要无条件把远期插值导数当成必须满足的终点条件。
3. 同时检查旧规划、上次下发目标、有效反馈和新模型目标的差异。差异过大时，不再强行沿用旧趋势，转入明确的保持或受控停止、重新观测流程。
4. 修复边界差分、过期轨迹和恢复控制的索引问题，再用与 G1 一致的串行路径建立真机对照，最后验证异步。

不能只缩短过渡时间：从 −1.37 急着追到 −0.38，可能造成更大的速度。也不能只把插值模式改成 `raw` 而保留 3.75 毫秒控制周期：当前执行器每次推进一个点，那会把原始动作按约 267 Hz 消耗，真正压缩执行时间。

需要补记全部 14 关节的融合前位置、速度、加速度、过渡时长、接入索引、融合后轨迹与反馈。现有单关节重建足以解释这个案例，但不足以验证整机所有异常和修改后的闭环效果。

## 附录 B 其他需要知道的行为

这些行为影响时序或任务表现，但尚未被证明是最大目标偏离的根因。

| 情况 | 当前行为与影响 |
|---|---|
| 预测全部过期 | 找不到晚于观测已用时间的点时，起始索引仍可能回到 0；应明确丢弃过期结果 |
| 首次发布、从可视化切到控制 | 索引可能重置为 0，随后先加 1 再取点；不总是按延迟选点 |
| 计算融合期间 | 旧控制线程还在推进，因此融合读取的旧点可能比最后提交点早一步 |
| 控制回调变慢 | 每次仍只推进一个点，通常使播放变慢，不会自动按真实时间追赶 |
| 推理返回空结果或普通超时 | 通常不更新轨迹，旧轨迹可能走到末点后重复下发；不能理解成自动停控 |
| 推理抛异常 | 推理循环会停止控制、清空动作状态并退避重试；与普通空结果不同 |
| 只停止推理 | 不等于停止控制；停止控制会禁用后续提交，并让队列中的旧批次失效 |
| Reset | 协调推理和控制、清空旧动作并执行复位；属于手动动作，不是模型预测 |
| 检查通过 | 形状正确、数值有限、状态新鲜且有控制权，不等于检查了关节运动范围或碰撞 |

夹爪另有处理：左夹爪保持启动控制时的反馈值；右夹爪先裁剪到 0～1，再做 `x⁴ / (x⁴ + (1−x)⁴)` 变换。当前每 9 次控制回调发送一次夹爪，频率接近 30 Hz；手臂没有这个分频。`gripper_offset` 表示将夹爪取点前移或后移，本次为 0。这些规则不解释手臂角度的直接放大，但会影响抓取时机。

观测按头相机时间参考匹配其他图像和状态，客户端还会压缩图像。这可能影响模型输入质量，但现有日志不足以证明它导致本次异常。语言、归一化文件、相机处理、夹爪映射应在与 G1 对照时保持一致。
